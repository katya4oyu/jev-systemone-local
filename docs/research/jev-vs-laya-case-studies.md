# Jev と Laya のケーススタディ調査(2026-09-29)

対象: TypeSafe の Jev(ホスト型 System One API)と、Convai Innovations の Laya(Apache-2.0、非自己回帰)。
本リポジトリは Laya の重みで Jev 互換 API を提供する。公開数値の多くは自己申告・非ペア比較で、日本語単体の公開数値は見つからなかった。日本語は本リポジトリのローカル実測(`eval/ja/`)で補った。

## 1. 主な出典

- [arXiv 2609.28940](https://arxiv.org/abs/2609.28940): pentest エージェントでの JEV/Laya 比較。NimbusCart 13脆弱性、条件ごとに1回のみの探索的研究で、著者自身が因果推論は不可と明記。
- [Laya GitHub](https://github.com/NandhaKishorM/laya) / [HF model card](https://huggingface.co/convaiinnovations/laya-multilingual)
- [Laya Ultrafast](https://systemonemodels.org/examples/projects/laya-ultrafast/): Browser Use の Jev 呼び出しを MLX 上の Laya に置換(M1 Max 中央値約33ms)。
- 比較記事: [laya-ai.com](https://laya-ai.com/laya-vs-jev)、[wavect](https://wavect.io/blog/laya-vs-jev-benchmark-ai-startup-moat/)、[dev.to](https://dev.to/jamilxt/jev-vs-laya-the-same-ai-idea-one-closed-and-one-open-3c6e)、[vanekt](https://vanekt.github.io/blog/laya-vs-jev/)、[laplusda](https://laplusda.com/en/posts/laya-local-system-one-model-guide/)

## 2. 使い勝手の違い(文献値)

| 観点 | Jev | Laya |
|---|---|---|
| 遅延 | p50 約236–410ms(ネットワーク込) | 約11–40ms(T4 / Apple Silicon、ウォーム時) |
| 文脈長 | 約4k〜64k と報じられる | 512 / 1,024(multilingual)。上限8,192だが約4k超は不安定と model card |
| 選択肢数 | 77ラベルでも実用(0.81–0.87) | 約20超で急落(0.36–0.43) |
| 汎用精度 | 高い(2ラベル 0.963) | ベース 0.34–0.36。微調整版のみ 0.766(ベンチ分割で学習済み) |
| 校正 | 比較的良好(ECE 0.144) | 過信気味(multilingual の平均信頼度 0.75–0.83) |
| score 型 | 使える | choice/noul より弱い |
| 微調整 | 不可 | 可 |
| コスト/データ | 約$0.042/1Mtok、外部送信あり | 推論費ゼロ、データは外に出ない(GPU・運用費は別) |

本リポジトリの「互換」は API 形状と SDK 接続のみ。重み・精度・速度・文脈長・確率は Jev と別物。

## 3. 有効なユースケース

- 低遅延が効く狭い判断(ブラウザ操作の「どの欄か」等)。オープンエンドな「次に何をするか」は不可で、固定ルールと併用する。
- 少ラベルの分類・ルーティング(問い合わせ振り分け、スパム/毒性、エスカレーション判定)。
- 外部送信できないデータ、高頻度で API 単価が効く場面、自社データで微調整できる場面。
- 不向き: 高カーディナリティ、長文、生成・推論、ラベル定義が曖昧なゼロショット。

## 4. 日本語のローカル実測

条件: Apple Silicon、本リポジトリのサーバ、`laya-multilingual-*` の3バックエンド。データは手書きの小規模セット(choice 24件、noul 20件、score 10件)。**n が小さいので ±10pt 程度の差は誤差**。jev は第6・7節で同じ入力を実測(第7節)。再現: `uv run jev-systemone-local` 起動後に `uv run python eval/ja/run.py`(`eval/ja/results.json` に全数値)。

### 遅延(ウォーム時、単発 / 5問バッチ p50)
MLX 7.2ms / 14.9ms、Core ML 7.9ms / 34.1ms、Core ML-ANE 4.8ms / 21.4ms。文献の11–40msと整合、Jev の約240ms+より1桁以上速い。

### 日本語の問い合わせ5分類(24件)とラベル数
| ラベル数 | 2 | 5 | 10 | 20 | 50 |
|---|---|---|---|---|---|
| MLX 正答率 | 0.92 | 0.83 | 0.79 | 0.79 | **0.33** |
| MLX ECE | 0.10 | 0.16 | 0.16 | 0.11 | 0.53 |

- 20ラベルまでは実用域、50ラベルで崩壊。文献の「約20超で急落」と一致。
- Core ML は 2〜20 で MLX とほぼ同等(0.79–0.92)。50ラベルは変換時の `max_options` 超過で 422。
- Core ML-ANE は 2ラベルのみ通り(0.92)、5ラベル以上は状態に4トークンしか残らず 422。実質、極短文の2択専用。
- ラベルを日本語で書いた場合 0.83、英語で書いた場合 0.79(差は誤差の範囲)。

### 毒性判定(noul、20件)
| 質問の書き方 | 正答率 | 攻撃的文への平均確率 | 穏当な文への平均確率 |
|---|---|---|---|
| 肯定形「攻撃的か」 | 0.70 | 0.41 | 0.00 |
| 否定形「攻撃的でないか」 | **0.35** | 反転後 0.65 | 反転後 1.00 |
| 英語の質問文 | 0.65 | 0.34 | 0.00 |

- 穏当な文の見逃しはなく、攻撃的な文の取りこぼしが多い(リコール低め)。閾値0.5では甘い。
- **否定形の質問は使えない**(README 記載の既知の弱点を確認)。noul は「〜か」の肯定形で書く。

### score(感想 → 5段階満足度、10件)
Pearson r = 0.96(数値は順序をよく反映)、MAE 0.45。一方、確率の argmax は両端に偏り、中間(「普通」)が0件。score は値そのものを使い、argmax は使わない方がよい。

### 文脈長(5分類、状態に無関係な日本語を足して測定。実トークン数)
| 入力トークン | 約200 | 約600 | 約900 | 約1.9k | 約3.8k | 約5.9k※ | 約7.9k※ |
|---|---|---|---|---|---|---|---|
| 問い合わせが末尾 | 0.79 | 0.71 | 0.75 | 0.58 | **0.38** | 0.33 | 0.50 |
| 問い合わせが先頭 | 0.79 | 0.79 | 0.71 | 0.71 | 0.71 | 0.92 | 0.92 |

※ 12件のみ。MLX は 8,192 まで 422 なしで動くが、**問い合わせ本文が末尾にあると約2k以降で劣化**する。先頭に置けば約8kまで概ね維持(ただし ECE は 0.13–0.19 で校正は悪い)。Core ML は 1,024 付近まで(893トークンで 0.71)、超過は 422。「8,192対応」は動作するだけで、精度は配置次第。

## 5. 結論(日本語での実用性)

- **使える**: 日本語の少ラベル(2〜20)の choice、肯定形の noul。速度と無料・ローカルが利点。5分類で約0.8は微調整なしのゼロショットとして悪くないが、本番判定には足りない水準。
- **注意**: 信頼度は過信(平均信頼度0.85–0.92に対し正答率0.79–0.83)。信頼度ゲートに頼らず、自前の保持データで再校正する。noul は攻撃的文の取りこぼしがあるため閾値を下げる。
- **避ける**: 50ラベル級、否定形の質問、score の argmax、長文で本文を末尾に置く構成。
- **Jev との差**: 文献では Jev が多言語・多ラベル・校正で優位(7言語 0.872 vs 0.544)。第7節で同じ入力を jev に流して実測し、差は文献より大きかった。
- 次の一手: 自社の実データで保持セットを作り、Laya の微調整前後を比較する(韓国語は微調整で 0.110→0.490 の報告あり。日本語は未検証)。

## 6. 追加検証: 会話・時系列・wiki への応用(ゼロショット)

全て MLX 版・ゼロショット・n は 40〜200 件。**AUC** は「確率で並べたときに正例が負例より上に来る割合」で、0.5 が偶然、1.0 が完全。閾値 0.5 の正答率は校正が悪く参考にならないため、AUC と最良閾値の正答率で見る。データは自作(会話・合成 wiki)と、実在の私的 wiki(約430ページ)から機械的に作ったラベル。スクリプトは `eval/ja/run_dialog.py` / `run_dialog_wordings.py` / `run_ts.py` / `run_wiki.py` / `run_wiki_variants.py` / `run_wiki_synth.py`。

### 会話ターン処理(音声・アバター)
| タスク | 結果 | 判定 |
|---|---|---|
| 発話の区切り(完結/継続中、60件) | AUC 0.44〜0.56(質問の書き方を7通り試した) | **使えない** |
| 途中で切った断片の検出 | AUC 0.51〜0.55 | 使えない |
| 応答/相槌/無反応の3択(45件) | 正答率 0.40(偶然 0.33)。相槌15件中14件を「無反応」と答えた | 使えない |
| 記憶すべきか(40件) | AUC 0.77〜0.79(「個人的な情報か」の noul、個人的事実/雑談の2択)。「記憶に保存すべきか」と聞くと 0.38 | 書き方次第で弱い信号 |
| 話題の逸脱(40件) | 最良は「同じ話題/別の話題」の2択で AUC 0.81、閾値0.4で正答率 0.75 | 弱〜中程度の信号 |

質問の書き方で結果が大きく変わる。区切りと応答選択は「今この人は何をしようとしているか」という語用論的判断で、ゼロショットの laya には無理と見るのが妥当(微調整前提)。

### 時系列
| タスク | 数値をそのまま入力 | ルールで作った日本語要約を入力 |
|---|---|---|
| 傾向(上昇/下降/横ばい、90件) | 0.22〜0.28(偶然 0.33) | **1.00**(長さ12・60とも) |
| スパイク有無(noul、60件) | 0.50(信頼度はほぼ1.0で過信) | 0.85(12点)/ 0.72(60点) |
| 次の値が上がるか(90件) | 0.59(単純な直近差分予測は 0.39) | 0.46 |

数値の解釈は laya に任せず、統計で言葉に直してから渡す構成が有効。値そのものの予測は根拠が得られなかった(次値は本質的に予測困難な合成データでもあり、上限は低い)。

### wiki(実在の私的 wiki 約430ページ、1ページ1センス規約、相対リンクあり)
| タスク | 結果 |
|---|---|
| リンク妥当性(既存リンク=正、同タグの未リンク=難しい負) | 長い文脈+要約を渡す noul は AUC 0.44(ほぼ全件「はい」)。入力を「言及語+候補タイトル」に絞ると **AUC 0.79**(80正+80負)、2択 choice は 0.71 |
| 同一センス判定(隣接段落 vs 兄弟ページの段落、各100) | AUC 0.38(偶然以下、常に「はい」寄り) |
| 合成データのリンク / 分割 / 重複 | リンク 0.69、分割 0.60、重複 0.56(2択 choice が noul より良い) |
| ページ種別(knowledge 4種、100件) | 正答率 0.92 だが多数派 0.96 で価値なし |
| ページ種別(memos 5種、47件) | 正答率 0.92(多数派 0.68)。ただし `capture` が30件と偏りが大きい |

- 使える形は「短い入力で、短い名前どうしの関連判定(候補の絞り込み)」。長い2文書の比較(同一センス、重複、分割)は使えない。
- 負例は「未リンク」なだけで本当は関連する可能性があり、実際の精度はここより高い可能性がある(下限に近い数字)。

### 総括
- **確率の並べ替えは使えるが、0.5 で切る使い方は使えない**。過信のため必ず自前データで閾値を決める。
- 有効: 短文の内容分類、要約経由の時系列状態判定、短い名前どうしのリンク候補判定。
- 無効(ゼロショット): 発話の区切り、応答/相槌の選択、長文どうしの同一性判定。これらは微調整が前提。
- 微調整は公式手順が強化学習ベースで、2×T4 で約4〜5時間(約3万問)。今回のローカル環境(PyTorch 未導入)では未実施。

## 7. jev(hosted, jev-1.13.0)との同一入力での実測比較

同じ自作データ・同じ質問を `api.typesafe.ai` の `jev-latest` に送って比較(2026-09-29、1回ずつ、n は各タスクの件数)。この表は合成データのみ。私的 wiki の抜粋は別途、この節の末尾で扱う。再現: `EVAL_BASE=https://api.typesafe.ai EVAL_MODEL=jev-latest EVAL_TAG=jev TYPESAFE_API_KEY=... uv run python eval/ja/run.py`(結果は `results_*_jev.json`)。

| タスク | laya(MLX) | jev |
|---|---|---|
| 5分類の問い合わせ 正答率(2/5/10/20/50ラベル) | 0.92 / 0.83 / 0.79 / 0.79 / **0.33** | 0.96 / 0.92 / 0.92 / 0.88 / **0.88** |
| 5分類 ECE(5ラベル) | 0.16 | 0.06 |
| 日本語ラベル / 英語ラベル | 0.83 / 0.79 | 0.92 / 0.92 |
| 毒性 noul 正答率(肯定形 / 否定形 / 英語質問) | 0.70 / **0.35** / 0.65 | 1.00 / **1.00** / 1.00 |
| score 感想5段階(Pearson r / MAE) | 0.96 / 0.45 | 0.99 / 0.13 |
| 長文(約7.9k tokens, 本文が末尾)正答率 | 0.50 | 1.00 |
| 発話区切り AUC(最良の書き方) | 0.56 | **0.999** |
| 記憶すべきか AUC | 0.79 | 1.00 |
| 話題の逸脱 AUC | 0.81 | 1.00 |
| 応答/相槌/無反応 正答率 | 0.40 | 0.67(相槌15件中6件のみ正解、9件は「応答」) |
| 合成 wiki: リンク / 分割 / 重複 AUC | 0.69 / 0.60 / 0.56 | 0.99 / 1.00 / 1.00 |
| 時系列(数値をそのまま入力)傾向 | 0.22〜0.28 | **0.97〜1.00** |
| 時系列(日本語要約を入力)傾向 | 1.00 | 1.00 |
| 次の値が上がるか | 0.46〜0.59 | 0.43〜0.46(どちらも偶然水準) |

- 第4〜6節で「laya は使えない/微調整が前提」とした語用論的タスク(発話区切り、記憶、話題逸脱、wiki 判定)は、jev ならゼロショットでほぼ解ける。laya の弱さはタスクの難しさではなく**モデル能力の差**。
- jev は質問の書き方にほぼ左右されず、否定形も問題ない。laya では書き方で結果が反転するため、jev 向けに書いたプロンプトをそのまま laya に流してはいけない。
- 発話区切りの「続きがありますか」形(AUC 0.015)は jev では完全に反転しているだけで(反転すれば0.985)、判断は正しい。
- jev でも応答/相槌の選択は0.67と弱く、相槌の判断は定義の曖昧さが残る。
- 時系列の予測(次の値)はどちらも偶然水準。数値をそのまま渡す傾向判定は jev だけ可能。laya は要約経由で同等になる。
- 遅延: jev の単発は約240ms(ネットワーク込)で文献どおり。laya は約7ms。

**使い分けの目安**: 応答の質が要る判断(発話区切り、記憶、話題分岐、wiki 整理)は jev。低遅延・ローカル必須で、ラベルが少なく、要約や短文に整えられる判断だけ laya。laya で jev に近づけるには微調整が要る。

### 実在の私的 wiki(約430ページ)での jev 比較
2026-09-29、ユーザーの許可を得て、私的 wiki(`notes/knowledge`・`notes/memos`)の抜粋を jev API に送って測定した。実行環境の自動判定がこの外部送信を拒否したため、ユーザーが手元で `!` 付きの同じコマンドを実行した。結果は集計値のみ(`results_wiki_jev.json`、`results_wiki_variants_jev.json`)で、本文は保存していない。ラベルは wiki 自身の既存リンク・ページ構造から機械的に作ったもの(第6節と同じ)。

| タスク(件数) | laya | jev |
|---|---|---|
| リンク妥当性 AUC(100正+198負、長い文脈+要約の noul) | 0.44 | **0.98**(最良閾値0.6で正答率 0.94) |
| 　同 閾値0.5の正答率(正 / 易しい負 / 難しい負) | 0.92 / 0.03 / 0.04 | 0.97 / 0.87 / 0.76 |
| 同一センス判定 AUC(隣接段落 vs 兄弟ページ、各100) | 0.38 | **0.84**(最良閾値0.35で 0.78) |
| 　同 閾値0.5の正答率(同一ページ / 兄弟ページ) | 0.72 / 0.09 | 0.59 / 0.87 |
| 質問形式の比較 AUC(80正+80負、入力を短くした形) | noul 0.79 / 2択 0.71 / 文脈付き2択 0.62 / score 0.42 | noul 0.996 / 2択 0.996 / 文脈付き2択 **1.00** / score 0.98 |
| 　同 長い入力の noul AUC | 0.44 | 0.92 |
| ページ種別 knowledge 4種(100件) | 0.92(多数派 0.96) | 0.52(多数派 0.96) |
| ページ種別 memos 5種(47件) | 0.92(多数派 0.68) | **0.96** |

読み取れること:
- **リンク判定は jev なら実用域**: 長い入力でも AUC 0.92〜0.98。laya は入力を極端に短く絞らないと 0.79 が上限で、長いと偶然以下。リンク候補の絞り込みは laya でも成立するが、確定判定は jev。
- **同一センス判定は jev でも難しい**: AUC 0.84 で、閾値0.5では同一ページの段落を「別概念」と見なしすぎる(0.59)。同一ページ内の隣接段落が同じ概念とは限らない(1ページに複数節がある)ため、正解ラベル自体にノイズがあり、実力は数字より高い可能性がある。閾値は 0.35 付近が良い。
- **knowledge の種別分類は両者とも価値なし**: 正解の大半が `concept`(96%)。jev は concept ページ100件中 45件を「synthesis / thinking」と判定した。laya の 0.92 は、ほぼ全件を concept と答えた結果にすぎない。jev の不一致が本当のラベル誤り(対比・考察を含む concept ページ)を拾っている可能性はあるが、個別確認はしていない。
- **memos の種別は jev 0.96 / laya 0.92**: どちらも使えるが、`capture` が31/47件と偏っている。
- 質問形式は、jev ではほぼ影響がなく、laya では大きく効く(第7節と同じ傾向)。

## 8. 微調整の実験(laya-multilingual → 日本語の会話ターン処理)

**結論: 数百〜千件規模の日本語データと約13分の訓練で、語用論的タスクが偶然水準から jev に近い水準まで上がった。** ただし質問の極性(否定形)への頑健さは獲得できていない。

### 方法
- **ベース**: `convaiinnovations/laya-multilingual`(mmBERT-base、322M)。公式の RLCD 手順(方策勾配+ソフト交差エントロピー)を、Kaggle ノートブックから単一デバイス版(MPS)に移植した(`eval/finetune/train.py`。損失・学習率・cosine・温度校正は公式のまま、DDP と GradScaler を除去)。
- **データ**: 4タスク(発話区切り849、応答/相槌/無反応645、記憶すべきか618、話題逸脱680)の日本語ラベル付き文を、Claude(opus)のサブエージェントに書かせた(`eval/finetune/data/`)。**jev の出力は教師に使っていない**(正解は0/1のハード分布)。各文を noul 形式と2択 choice 形式、複数の言い回しに展開して 5,026 件を学習。10% は行単位で dev に取り置き、その半分を温度校正に使用。
- **評価**: 第6・7節と同じ、別のサブエージェントが書いた評価データ(データは学習側と別、近似重複は短い定型句10件のみ)。件数は40〜60で、**誤差は大きい**。
- **設定**: 4エポック、実効バッチ32、encoder 2.5e-5 / head 1e-4、fp32(この Mac では bf16 より約2倍速かった)。約 23 件/秒、合計 **約13分**(M4 Pro 48GB)。校正温度は choice 7.07 / noul 6.88 と高く(強い過信を補正)、laya / laya-mlx は温度を 0.5〜5 に切り詰めるため、以下の評価はどちらのランタイムでも実効 5.0 で行った。

### 結果(AUC。2択 choice 形式 / noul 形式)
| タスク | laya ベース | **laya 微調整後** | jev |
|---|---|---|---|
| 発話区切り | 0.56 / 0.48 | **0.97 / 0.93** | 0.999 / 0.95 |
| 途中で切った断片 | 0.55 / 0.51 | 0.82 / 0.87 | 0.97 / 0.93 |
| 記憶すべきか | 0.60 / 0.55 | **0.985 / 0.995** | 1.00 / 1.00 |
| 話題の逸脱 | 0.67 / 0.72 | **0.98 / 0.96** | 1.00 / 1.00 |
| 応答/相槌/無反応(正答率) | 0.40 | **0.93** | 0.67 |

- 閾値0.5の正答率でも、発話区切り 0.88〜0.90、記憶 0.93〜0.98、話題逸脱 0.85〜0.93。校正温度の効果で、ベースでは効かなかった 0.5 閾値がほぼ使える。
- **応答/相槌/無反応は jev(0.67)を上回った**。jev はこのタスクの「相槌」の定義を掴めなかったが、学習データで定義を教えた laya は 0.93。
- 単発の推論は PyTorch/MPS で約 11ms(MLX サーバは約 7ms)。

### 副作用(回帰確認)
| 確認項目 | ベース | 微調整後 |
|---|---|---|
| 日本語5分類(2/5/10/20/50ラベル)正答率 | 0.92 / 0.83 / 0.79 / 0.79 / 0.33 | 0.88 / 0.83 / 0.79 / **0.71** / **0.21** |
| 同 ECE(5ラベル) | 0.16 | 0.22 |
| 毒性 noul(肯定形 / 否定形 / 英語) | 0.70 / 0.35 / 0.65 | **0.95** / 0.25 / **0.90** |

- 多ラベル分類は微妙に劣化した(20ラベルで 0.79→0.71)。会話タスク特化の微調整の代償。多ラベルには別チェックポイントを使うか、混ぜて再訓練する。
- 毒性 noul は学習していないのに改善(0.70→0.95)。noul の一般的な扱いが良くなった可能性がある。

### 限界と注意
- **質問の極性の反転は学習できていない**。「話題が変わりましたか」(反転形)の AUC は 0.075、「続きがありますか」は 0.78(本来の向きなら逆になるはず)、否定形の毒性は 0.25。微調整後のモデルは、質問文の意味ではなく**タスクの文脈に対する学習済みの判断**を返している。使うときは、学習した言い回し(肯定形)に固定する。
- 学習データと評価データは、どちらも Claude が書いた自作の会話文。実際のユーザー発話や ASR 誤りとは分布が違う可能性が高く、**実運用の精度はこの数字より低いと見るべき**。EOU の学習データは、完結側が継続側より長い(平均11 vs 8文字)ため、長さが手がかりになった可能性もある。
- 件数が少なく、1回の訓練・1シードのみ。ばらつきは未測定。
- 発話区切りは、断片(途中で切った文)に対する精度が 0.82〜0.87 に留まる。リアルタイムの区切り判定には、さらに ASR 由来のデータでの学習が要る。
- 重み(約650MB)はリポジトリに含めていない。再現は `eval/finetune/` の3スクリプト(`build_items.py` → `train.py` → `eval_ft.py`)。`laya-mlx convert` で MLX 形式に変換でき、このリポジトリのサーバに `JEV_LOCAL_MLX_MODELS` で追加できる(README「微調整したモデルを載せる」)。MLX サーバ経由の評価は PyTorch と同じ精度、単発 7.5ms だった。

## 9. Jeff / Kev のローカル実測(2026-09-30)

### 対象
- **Jeff**([firelex/jeff](https://github.com/firelex/jeff)): TypeSafe とは無関係の独立プロジェクト。Qwen3.5 の全重み微調整。今回は 0.8B / 2B(MLX)を実行。README は英語のみで、日本語は公式には未検証。選択肢は最大26個。
- **Kev**([jaredpalmer/kev](https://github.com/jaredpalmer/kev)): Qwen3.5-Base に LoRA(rank 16)+ pointer head。今回は 0.8B / 4B(MLX、bf16)を実行。日本語は公式に明記なし。同名の別プロジェクト [arjun988/Kev](https://github.com/arjun988/Kev) とは別物。
- どちらも `/v1/systemone` 互換のローカルサーバとして起動し、第4〜8節と**同一の評価データ・同一のスクリプト**(`eval/ja/run_all.sh`)を流した。Mac は M4 Pro 48GB、1台ずつ順番に実行。Jeff の実行には uv 0.12.19 以上が要る(mise で 0.12.20 を追加インストールし、既定バージョンは変更していない)。

### 読み取れること
1. **日本語のゼロショットは、Qwen 系の Jeff/Kev が laya より圧倒的に良い**。公式には英語向けだが、ベースの Qwen3.5 の日本語力で、分類・長文・記憶・話題逸脱・wiki のリンク判定は jev に近い(0.9〜1.0)。laya の日本語ゼロショットの弱さは、ベースモデルの規模と学習の差が原因と考えるのが自然。
2. **Kev-4B が最も jev に近い**(5分類 1.00、否定形の毒性 1.00、時系列 0.99、長文 1.00)。Kev-4B は遅延 47ms(単発)/149ms(5問)で、jev の API(約 240ms、ネットワーク込)より速い。**Jeff/Kev の小型(0.8B)でも分類は 0.9 前後**あり、10〜27ms で動く。
3. **語用論的なタスク(発話区切り、応答/相槌の選択)は、Jeff/Kev もゼロショットでは弱い**(発話区切り AUC 0.6〜0.88、応答/相槌 0.36〜0.67)。jev でも応答/相槌は 0.67。ここは**日本語で微調整した laya(0.97 / 0.93)が最良**で、速度も 7〜11ms と最速。
4. **否定形の質問への頑健さ**は Kev-4B(1.00)と jev(1.00)が突出。Jeff/Kev の小型は 0.70〜0.75、laya は 0.35(微調整後 0.25)。
5. **選択肢の上限**: Jeff は最大26個で、50ラベルの試験は全件エラー。Kev-0.8B は 0.75 に低下、Kev-4B は 1.00。
6. **長文**: どちらも約8kトークンまで 0.92〜1.00 を維持(Kev の学習は 384 トークンまでだが、実際には崩れなかった)。laya は 0.38〜0.50 に落ちる。

## 10. モデル推薦エンドポイント(`/v1/recommend`)の検証

やりたいことのテキストから用途を判定し、これまでの実測値(第4〜9節)をもとにモデルを順位づけする、Jev にない独自 API。README「モデルのおすすめAPI」。

### 用途の判定(10種類)
評価データ 120 件(Claude が書いたリクエスト文、10 用途 × 12)を、学習には使わずに取っておいた。

| 方式 | 正答率(全体 / dev 60 / test 60) |
|---|---|
| laya ゼロショット(用途ごとの説明文を付けた 10 択) | 0.21 / 0.22 / 0.20 |
| laya ゼロショット(説明文を短く書き直した 10 択) | dev 0.57〜0.60(書き方だけで 0.22 → 0.60) |
| キーワード規則のみ | 0.34 |
| キーワード + laya の併用 | 0.42 / 0.50 / 0.33 |
| **文字 n-gram 分類器**(学習 750 件) | **0.89 / 0.92 / 0.87** |
| 　+ 依頼文中のラベル数で少数/多数分類を補正 | **0.91 / 0.92 / 0.90** |

- laya のゼロショットは、長い依頼文の 10 択が苦手で、説明文の長さで結果が 0.22〜0.60 と大きく変わった。laya やキーワードを分類器に混ぜても、精度は上がらず、むしろ下がった(0.91 → 0.88)ため、最終形は分類器のみ(判断モデルは呼ばない)。
- 学習データ 750 件は、別々のサブエージェント 3 つが、文体(エンジニア風、非エンジニア風、短文から長文まで)を変えて書いた。評価データとの一致は完全一致 0 件。
- 確信度は使える: 0.5 以上の 88 件で正答率 0.98、0.7 以上の 72 件で 1.00。正解時の平均確信度 0.74、誤り時 0.37。主な誤りは「少数分類 ↔ 多数分類」(5 件)で、ラベル数の規則で一部を解消した。
- 用途ごとの正答率(分類器のみ): 話題逸脱・有害検知・時系列・文書間・その他は 1.00、ターン制御 0.92、段階評価 0.92、多数分類 0.75、記憶判定 0.83、少数分類 0.50。
- 応答時間はプロセス内で 0.05ms/件。

### 制約の読み取り(パターンによる検出、test 60 件)
| 制約 | 適合率 | 再現率 |
|---|---|---|
| ローカル限定 | 1.00 | 0.88 |
| 低遅延 | 1.00 | 0.67 |
| 長文 | 1.00 | 1.00 |
| 否定形 | 0.50 | 0.33 |
| ラベル数(値も一致) | 1.00 | 0.60 |

パターンは dev 60 件の取りこぼしを見て一般化した。test は調整に使っていない。否定形とラベル数の再現率が低いので、重要な条件は `constraints` で明示するのが確実。

### 限界
- 評価データ・学習データはどちらも Claude が書いた文。実際の開発者の書き方より整っている可能性が高く、実運用の精度はこの数字より低いと見るべき。
- 推薦の順位づけは、第4〜9節の小サンプルの実測値をそのまま能力表にしたもの。件数が少なく、1 回計測。ラベル数や遅延による減点の重みは経験則で、検証していない。
- Jeff・Kev・Jev 本体はこのサーバでは提供しておらず、推薦で「起動方法」を返すだけ。

## 11. 限界

n が小さく、データは自作でドメインが狭い(EC 問い合わせ、短い会話台本)。計測は1回のみ。jev はホスト型で内部が不明のため、差の原因(モデル規模・学習データ・前処理)は特定できない。文脈長テストの無関係文は同一の繰り返しで、実文書とは性質が違う。
